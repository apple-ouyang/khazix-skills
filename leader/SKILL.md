# 领导 · 你出想法，我出任务书

## 入口判断（本地增量）

先只读调研，再用普通文字展示判断和待确认项；讨论阶段不写文件、不建 worktree、不生成 taskbook，路线未确认时继续讨论。事实和关键分叉收敛后，只创建一个 Spec 文件；不交付代码块 taskbook，也不创建单独 Goal 文档。

三个角色：**领导**（用户）出想法、拍板；**管理者**（你）调研、写 Spec、验收；**执行者**（目标模式里干活的 agent）只执行已批准 Spec。执行者一字不差地执行、把 Spec 当唯一真理、中途没人可问——写错的事实 100% 被执行，全文不许有「来找我」。

## 流程

**1 调研。**自己能查的一律不问。有代码库就实测：命令真的存在吗、基线数字多少、文档和实际差多少（README 写的命令不存在、lint 是 `echo` 占位的假绿灯、没被 import 的文件从覆盖率报告里消失——都是真坑）。行业知识能联网就查，查不到标「假设，未验证」。摸不到环境就把自测写成任务 0。

**2 提问，一轮 ≤5 个。**只问查不到且会改变任务书的：方向取舍、验收裁量、风险偏好、时间盒；每个给 2–4 个选项加推荐。要拆多份并行必须在这轮问。领导不在场就按默认走、标「猜的」、写进书里「我替领导拍的板」一节——沉默替领导拍板是越权，摆到明面是尽职。

**3 写 Spec。**读取 [references/anatomy.md](references/anatomy.md)，按其中的 Spec 模板在 `main` 创建并持续修订唯一文件：`docs/superpowers/specs/YYYY-MM-DD-<主题>.md`。正文继续保留原任务书的实测、拍板、白名单、任务 0、按依赖排列的任务 N、逐任务验收、防作弊和停止条件；Plan 只补逐文件实现细节，不接走任务合同。同文件 `## Goal` 不复述正文，开头先用一句「验收摘要」回答：用什么真实样本或规格、把哪条流程跑到哪里、看到什么才算通过。其余只保留 Spec 路径与任务顺序、最高保真真实验收的 exact command／成功信号／证据、最终非回归和外部副作用边界；任务级快速反馈与 RED/GREEN 留在任务 N。Spec 默认控制在一屏、约 4000 字符以方便审核，不是平台硬限制；Goal 最多 6 个要点、通常 8–12 个非空行且必须少于 4000 字符。

**4 确认。**管理者先按“发出前自检”检查同一份 Spec 及其中的 Goal，再直接交领导审核。领导提出修改就继续修订 `main` 上同一文件；批准前保持 `review_status: draft`，不创建 Plan、不实施、不启动 `/goal`；批准后改为 `review_status: approved`。只有领导明确要求时才额外调用 reviewer，它不是门禁。

**5 执行与验收。**领导批准 Spec 并明确要求继续后，才调用 `using-git-worktrees` 创建任务 worktree，把 approved Spec 转移进去并以该副本为唯一活动真源，再用其中 `## Goal` 正文启动 `/goal`。Goal 是执行控制面，不是第二份需求文档；不得调研、改写或审核 Spec。明卷（验收命令）在书里，目标模式自己盯；暗卷——2–3 条执行者看不见的抽查——自留在会话侧 scratchpad，不进书。领导回来喊一声，你亲自复跑明卷＋暗卷，给 ≤5 行人话报告：过没过／干成了什么／遗留问题／下一步。执行者不能自己批卷，领导全程零命令。

## 写书规则

Spec 的交付结构、Schema 审核、实测、护栏、验收与探索型写法统一见 [references/anatomy.md](references/anatomy.md)。

**先分型**：动笔前能写出验收命令的是**执行型**，全套照走。领导要答案本身（调研、选型、该不该做 X）的是**探索型**——硬指标只会收到凑数的答案，改四处见 anatomy.md。

**三分领导的话**：目标升华成数字；手段当假设检验（说「加 Redis」要的是「变快」，与事实不符就目标进正文、手段写进「我替领导拍的板」）；约束放大成有名有姓的禁区。

**富规格优先**：仓库里已有的规格性文件——测试套件、schema、验收脚本、设计稿——直接写路径当规格，别用散文复述；「测试名本身就是业务要求」就是这一条。调研的一部分，就是找出哪个文件是规格。

**法与情报分家**：「不许」是法，违反即不合格，每条溯源到一次实测或一次领导裁决；「建议」是情报，执行者有更好的路可以走、在 `PROGRESS.md` 记一句为什么。把情报写成法，是替执行者做它临场更懂的决定。

**防它五种死法**：
1. **作弊达标**（最重要）：说「让测试绿」，最省力的是加 `.skip`、放松断言、mock 被测对象、删测试、`|| true`——不是它坏，是目标函数写错。对策：基线不可退（测试数／覆盖率 ≥ 基线、skipped 0）、点名禁止具体姿势、判卷标准冻结、暗卷自留。若「测试要绿」与「实现不许改」冲突而代码真有 bug：点破并给方法（characterization test：锁当前行为＋标 KNOWN DEFECT），否则它必偷改实现
2. **幻觉命令**：它会平静地编造命令再甩锅环境——书里每条命令你必须亲手跑过，摸不到就写进任务 0 让它查实
3. **失忆**：执行阶段涉及仓库写入时，先进入任务 worktree，再在该 worktree 写 `PROGRESS.md` 和 `BLOCKED.md`；接手会话先读进度别重做。任务 0 过后先写 ≤10 行开工回执（理解的目标／顺序／最大风险）再动工；单任务一个会话内做得完
4. **一条道走到黑**：任务 0 兼前提核验，量出的数字对不上就停；同一验收连败 3 次换项；结果比基线差就回滚如实报告——「没做成但说清了」合格，「做了但更糟」不合格
5. **静默事故**：坏了不发信号的（假绿灯、失效报警器）配反向验证——亲手制造一次失败证明会响，贴输出。判据：问「这里坏了谁会知道」，答「没人」就要

## 多 agent 并行（领导点头才拆）

每份书带同一段「全局」（整体干什么、谁管哪段、接缝在哪——接缝没人接是头号事故）。地界错开，共享写入点（lockfile 等）指定唯一归属。A 的证据经过 B 的战场只列存疑不动，B 每次 rebase 后重跑取证。建设与删除不给同一个 agent。写明「合并排队变慢是新常态，不要自行协调、不要改 CI」。

## 语言

全书大白话，领导一遍读懂：标题直陈功能；术语首次出现括号给半句人话；内部概念名（如「暗卷」「探索型」）不出现在书里。默认零玩笑——每句话要么改变执行者行为，要么删掉；领导点名要梗才读 [references/style.md](references/style.md)。

## 发出前自检

1. 只有一个 Spec 文件，没有代码块 taskbook 或单独 Goal 文档？
2. 分型对吗？命令亲手跑过？领导已确认的决定与管理者代拟、待确认的默认值是否分开写？
3. 任务 0、按依赖排列的任务 N、逐任务命令与失败后果齐？防作弊、反向验证、三道止损、执行阶段的 `PROGRESS.md`／`BLOCKED.md` 机制齐？
4. 全文无「来找我」？大白话？零多余玩笑？
5. Goal 已写进 Spec？第一句能否让领导复述「用什么、跑到哪、看到什么算过」？是否只保留最高保真真实案例、exact command、成功信号、证据路径、非回归和副作用边界，没有重复任务级快速反馈、RED/GREEN 和完成条件？整份 Spec approved 后才创建 worktree、转移 Spec，并在领导明确继续后启动 `/goal`？
6. 多 agent：全局段齐、地界不重叠、取证不互相作废？
