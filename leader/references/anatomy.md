# Spec 与任务书 · 结构规格

正式交付使用下面的 Spec 模板。保留原任务书的实测、拍板、地界、任务、规矩和完成条件，但映射进模板，不重复创建一套平行标题。单任务正文通常 1500–2000 字符。本规格不配样文——照规格自己写，措辞贴合当下的任务，别套任何现成句式。

## Spec 格式

除 `## Goal` 外只保留适用章节，没有内容的标题直接删除；`## Goal` 始终保留并随整份 Spec 一起批准：

```markdown
---
summary: 一句话说明这份 Spec 要改变什么
doc_kind: spec
status: active
review_status: draft
---

# [任务名称]

## 这活为什么干

[当前问题，以及完成后用户能得到什么结果。]

## 领导已经拍板

- [只写领导明确提出或逐项确认的决定。]
- [要求冲突时的取舍顺序。]

## 我替领导拍的板（待确认）

- [只写管理者根据调研代拟、但领导尚未确认的默认值。]
- [尚无证据但必须先采用的决定，明确标注「猜的」及猜错代价。]

## 范围与非目标

- [允许改变的业务能力、模块和外部行为。]
- [明确保持不变的内容。]
- [不做哪些容易顺手扩张的事情。]

## 改完后是什么样

- [用户或调用方可以观察到的行为。]
- [真正影响审核的 API、schema、权限、迁移或兼容合同。]

## 现状与任务 0

- [带来源和日期的实测基线；查不到的标「猜的，没验证」。]
- [开工前必须运行的前提核验命令；数字或合同对不上时如何停止。]

## 任务 1：[结果名称]

- 目标：[可观察结果和数字。]
- 顺序：[从哪下手、依赖什么，以及为什么排在这里。]
- 死规矩：[必须做什么；违反后的具体后果。]
- 验收：`[命令]`；[机器可判的通过条件。]
- 反向验证：[如何制造一次预期失败、还原并重新通过。]

## 规矩

- [白名单、防作弊、依赖或权限边界。]
- [连续失败、基线变差和不可逆操作的停止条件。]

## 完成条件

- [证明目标成立的整体证据。]
- [证明迁移完整、旧入口清除和失败行为正确的证据。]
- [必要的反作弊条件和停止条件。]

## 待确认

- [只写会改变范围、行为或验收的问题；没有则删除。]

## Goal

- 验收摘要: 用[真实样本、现有规格或真实读者任务]把[流程／操作]跑到[明确 stage 或边界]；看到[一至三个核心成功信号]才算通过，并且[最重要的副作用禁区]。
- 执行依据: `docs/superpowers/specs/YYYY-MM-DD-<主题>.md` 的任务 0 → N；任务级快速反馈、RED/GREEN 和反向验证只按正文执行，不在这里复述。
- 真实验收: [样本]｜[场景与目标 stage]｜`[能完成并判定该场景的 exact command]`｜成功=[机器信号]｜证据=`[artifact / report / screenshot path]`。
- 非回归: `[最终 broad command]`。
- 边界: [允许与禁止的 live data、上传、花费、权限或 mutation；关键前提不成立时停止。]
- 交付: 汇报实际命令、结果、证据路径和未完成项；验收未满足时不得宣称完成。
```

Goal 是执行控制面和领导的验收索引，不是第二份任务书。第一句必须让不读后文的领导知道「用什么、跑到哪、看到什么算过」；如果一句话塞不下多个独立能力，就增加一条“真实验收”，每条绑定一个样本，不用抽象总目标掩盖。整个 Goal 最多 6 个要点；产品决策、架构取舍、任务级快速反馈、RED/GREEN、反向验证和完整验收都留在同一 Spec 正文，Goal 不能复制它们凑成第二套检查表。每个执行型 Goal 至少绑定一个最高保真、不会越权的真实案例；真实数据不等于真实 mutation，上传、花费、权限和 live 写入仍需单独授权。最终命令只负责创建或提交任务却不能证明流程已到目标 stage 时，必须再给可复跑的等待、推进或判定入口；该入口尚未实测时，在“真实验收”中用一句话标出缺口并保持 draft，不展开新的任务步骤，也不编造命令。无法提供真实案例时，写明原因、替代证据与剩余风险，否则保持 draft。纯文档、研究或 Skill 任务分别使用真实读者任务、可复跑来源检查或 prompt-based Eval，不强造业务 E2E。scorecard、working memory 和 human control surface 只在多轮优化或长时间实验确有需要时加入。

管理者只是把领导原意整理成可执行措辞时，仍写入“领导已经拍板”；只有补充了领导未确认的默认值或取舍，才写入“我替领导拍的板（待确认）”。批准后两类决定都成为执行合同，标题只保留来源。

## Schema 审核

只要本次会新增、删除或修改 JSON、API payload、artifact 或数据库 schema，就必须在“改完后是什么样”中给出用户可直接审核的具体例子，不能只写字段表或抽象描述：

- JSON/API/artifact：给出最小的修改前与修改后完整样例，使用真实字段名、类型和值；条件字段或失败 shape 会改变合同判断时一并给例子。所有 JSON 样例使用 `json` fenced code block、2 空格缩进且每个 key 单独成行；多字段 object 或多元素 array 不得写成单行 compact JSON。
- 数据库：给出具体 DDL 或 schema 前后片段；涉及历史数据迁移时，再给一条真实形态的旧记录如何变成新记录。
- 每个新增字段说明谁写、谁读、当前用途和如何验证；缺少当前消费者的字段不进入 Spec。

具体例子属于用户批准合同。例子缺失、与正文不一致或仍有会改变 shape 的待确认事项时，保持 `review_status: draft`，不得批准或执行。

Spec 必须保留能让 agent 独立跑完的任务顺序：任务 0、任务 N 的结果、依赖、失败后果、验收和必要反向验证。逐文件实现清单、worker 分工、commit 边界和 worktree 合入细节才属于可选 Plan；Plan 只能展开实现，不能接走或改写 Spec 的任务合同。`PROGRESS.md` / `BLOCKED.md` 在执行阶段创建，存在时作为执行证据索引，不能替代 Spec 或实际验证。Goal 不重复 Spec 或 Plan 内容，只指向同一 Spec 的任务顺序。

## 原任务书内容规则

写 Spec 时保留下面会决定 agent 能否独立完成的任务合同；措辞可以压缩，但不能把任务顺序、逐任务验收或失败后果全部留给后续 Plan。

## 开头（不带标题，五件事各一句）

- 你是执行者，这份 Spec 是你唯一的任务来源；涉及仓库写入时先进入任务 worktree，拿不准的写进该 worktree 的 `BLOCKED.md`（待裁决清单），跳过继续做别的，最后随交付提交
- 断了、换新会话：先读同一 worktree 的 `PROGRESS.md`（进度记录）接着做，别重做；每做完一项立刻按 Spec 完成条件更新 `pending / in_progress / verified / blocked`、最新验证命令和证据路径。Spec 审核阶段不创建这两个文件
- 这活为什么干：一句意图，为什么干＋干完世界什么样——书里没写到的情况，执行者靠它自己裁
- 两个要求打架时的让步顺序（如「算得对 > 做得全 > 做得快」）
- 死规矩与参考的分界：「只允许」「不许」违反算失败；「建议」有更好的路就走，在 `PROGRESS.md` 记一句为什么

## 我替领导拍的板

领导已确认的决定写入“领导已经拍板”。没问出口、由管理者代拟的每个决定写入“我替领导拍的板（待确认）”：问题 → 默认值（标「猜的」）｜猜错的代价。领导审核时可改；执行者按批准 Spec 里的默认走，不停下来等。
写不出机器可判命令的目标（文风、体验类）也记在这里：改成抽查点＋领导亲验，注明这活只能半托。

## 界限

- 白名单：只允许改哪些路径＋新建文件，其余只读——用白名单不用黑名单，黑名单永远列不全
- 判卷标准（测试、验收脚本、CI 配置）碰都不许碰；无 git 时给每个文件的 sha256 指纹（文件内容的数字摘要，交付时必须一字不差）
- 点名最诱人的顺手活（那个一行就能修的 bug、顺手重构、顺手装工具），写明进 `BLOCKED.md` 待裁决；收不回的操作（删数据、改权限）停下写 `BLOCKED.md` 做别的

## 现状与任务 0

- 实测数字逐条带来源与日期，查不到的标「猜的，没验证」；能提前实证的关键结论（如「只改实现就能全绿」）写进来，提前拆掉借口
- 任务 0：跑指定命令核对上面的数字，不存在的命令、空转的假检查当场记 `BLOCKED.md`；对不上就停，证据写 `BLOCKED.md` 最上面，只做不受影响的部分；核对无误后把「理解的目标／顺序／最大风险」≤10 行写进 `PROGRESS.md` 再动工

## 任务 N

每个任务包含：一句话目标带数字；从哪下手一句（多任务按依赖排序，说清为什么它排前面）；死规矩写成「做 A，否则 B」并带具体后果；验收＝命令＋机器可判的判定（含防漏判定，如「跳过 0」）；反向验证＝故意制造一次失败、贴变红输出、还原后贴全绿——凡是「坏了没人会知道」的检查都要这一步。

## 规矩

- 防作弊点名到具体姿势：跳过测试（skip/todo）、放宽判断、把被测对象换成假的（mock）、删测试、改阈值或验收脚本、`|| true`（失败也当成功）——全算失败；测试数／覆盖率只许 ≥ 基线；补测试类任务加「实现目录 `git diff` 为空（业务代码一行没动）」
- 不新增流程、权限、依赖，必须加的写 `BLOCKED.md`
- 同一条验收连败 3 次换下一项；结果比开工差就回滚如实报告——「没做成但说清了」合格，「做了但更糟」不合格
- 项目自有纪律（分支／PR 规则、提交前检查）写在这里

## 完成条件

- 两条硬指标：一条度量领导要的结果（不是工作量），一条守约束（指纹没变、回滚＝0 之类）
- 一句「每条都要在对话里贴实际命令输出（含反向验证的红→绿证据），只说做完了不算」——判完成的小模型不跑命令、不读文件，只认对话里贴出的内容
- `BLOCKED.md` 随交付提交；未解决的偏差、跳过、降级、范围外发现和未验证项都要保留。逐条对照 Spec 完成条件后确实没有剩余项，才写「无」
- 止损：「或已跑满 N 轮——满轮即停，如实汇报卡在哪、还差什么」

## 探索型：改四处，其余同款

领导要的是答案本身（调研、选型、「该不该做 X」）时，硬指标只会换来凑数的答案：

1. 完成条件换成学习目标：结论条数设上限、每条附来源与日期或可复跑的复现步骤——宁收 2 条实的，不收 10 条凑的
2. 预算换成可承受损失：最多烧多少时间／查多少来源，烧完就交卷，交「目前最优＋还没排除什么」
3. 防作弊主防编造：凑数的结论、查无此文的引用、没跑过的「实测」都算作弊；每条结论要经得起领导随机抽一条、10 分钟内复现
4. 此路不通＝合格交付：带证据证明某方向是死路（死因＋原始输出），按完成计
